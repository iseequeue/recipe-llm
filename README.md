# Шеф-LLM: рецепты на русском — LoRA vs RAG на YandexGPT-5 Lite и Qwen2.5

Модель пишет выполнимый рецепт по названию блюда, списку продуктов или категории. В проекте сравниваются
два способа это получить: **дообучение (LoRA SFT)** и **генерация с поиском по базе рецептов (RAG)** на двух
базовых моделях близкого размера: `yandex/YandexGPT-5-Lite-8B-instruct` и `Qwen/Qwen2.5-7B-Instruct`.
Получилось 8 систем (2 модели × {без дообучения, LoRA} × {без RAG, RAG}). Все они оцениваются на одном и
том же наборе запросов, у каждой оценки есть бутстрэп-доверительный интервал.

Полный цикл: сбор и очистка данных → отбор примеров LLM-судьёй → LoRA SFT на одной V100 → RAG-индекс →
автометрики с доверительными интервалами и слепое SBS → веб-демо. Эксперименты логируются в MLflow.

## Главное

Цифры — по 200 запросам, в скобках 95% бутстрэп-интервал; эффекты считаются парно на одних и тех же запросах.

1. **Знание классических блюд модель получает на предобучении, дообучение его не добавляет.** YandexGPT
   без дообучения называет ключевые ингредиенты классики в 99% случаев (в борще есть свёкла, в сырниках
   творог), Qwen — в 79%. LoRA на 10k рецептов меняет у Qwen +3 п.п. [−3; +10], то есть неотличимо от нуля.
2. **RAG закрывает пробелы в знаниях.** Три найденных рецепта в промпте дают Qwen +17 п.п. [+9; +26]
   (79 → 96%), дообученному Qwen +15 [+10; +22] (82 → 98%). У базового Qwen заодно на 24 п.п. меньше
   обрывов и на 23 п.п. лучше используются ингредиенты. YandexGPT уже у потолка, ей RAG почти ничего не даёт.
3. **Дообучение даёт формат и стиль, но вместе с ними переносит недостатки данных.** Qwen после LoRA
   перестаёт обрывать ответы (36% → 0%) и использует в шагах почти все ингредиенты из списка (63 → 93%).
   У YandexGPT, наоборот, становится меньше количеств у ингредиентов (−10 п.п. [−13; −7]) и в 2,5 раза
   больше «болтовни» форума (30 → 76%) — ровно то, чем грешат исходные рецепты povarenok.ru.
4. **LoRA и RAG не складываются.** С найденными рецептами в промпте дообученные модели хуже используют
   ингредиенты (−5…−7 п.п.), реже указывают количества (−4…−11) и начинают обрывать ответы. «Болтовня» у обеих
   сходится к 46%: модель перенимает стиль найденных рецептов (у YandexGPT −30 п.п., у Qwen +20). При обучении
   модели не видели контекста в промпте; следующий шаг — обучать на промптах с найденными рецептами
   (RAFT-подобная схема).
5. **Дешёвый LLM-судья согласуется с сильной моделью умеренно, но отбирает в верную сторону.** Для проверки
   120 рецептов вслепую оценил DeepSeek в режиме рассуждений: ρ Спирмена = 0.41 [0.24; 0.55]. Среди отобранных
   в обучение плохих рецептов 4%, среди отброшенных 13%, хороших — 72% против 50%. Но на 120 рецептах
   интервалы этих долей перекрываются.
6. **Выбор базовой модели под язык важнее дообучения.** YandexGPT без дообучения точнее дообученного Qwen
   по ключевым ингредиентам (99% против 82%) и не обрывает ответы.

## Данные

| Источник | Что даёт |
|---|---|
| [`d0rj/povarenok_recipes_detail`](https://huggingface.co/datasets/d0rj/povarenok_recipes_detail), Apache-2.0 | 154k рецептов: ингредиенты с количествами, шаги, категории, просмотры |
| [`dim/povarenok`](https://huggingface.co/datasets/dim/povarenok) | рецепты того же сайта с лайками; используются как сигнал качества, джойн по id рецепта |

Открытого редакционного датасета рецептов на русском нет, поэтому основная работа — отбор.

1. **Правила** (`scripts/build_dataset.py`, для каждой причины отказа ведётся счётчик): 3–25 ингредиентов,
   3–20 шагов, русский текст, без ссылок, без «как на фото». Не меньше 40% ингредиентов должны
   упоминаться в шагах: так отсекаются рецепты, где список не сходится со способом приготовления. Затем
   дедуп по нормализованному названию и топ-24k по популярности (просмотры + лайки).
2. **LLM-as-judge** (`scripts/score_recipes.py`). Базовая YandexGPT оценивает рецепт по рубрике 1–5.
   Текст не генерируется: оценка — матожидание распределения следующего токена по цифрам 1–5. Это один
   forward-проход на рецепт (`logits_to_keep=1`), детерминированно, и оценка непрерывная, а не одна
   из пяти цифр. Скоринг шардируется на 4 GPU, итог сливает последний завершившийся шард под файловой
   блокировкой. В обучение идут 10k лучших.

![Распределение оценок LLM-судьи](eval/figures/judge_scores.png)

**Проверка судьи более сильной моделью** (`scripts/make_judge_labeling.py`). 120 рецептов, поровну из каждого
дециля оценки судьи, вслепую оценены DeepSeek в режиме рассуждений по шкале 1–5: оценки судьи он не видел,
порядок перемешан. Поскольку децили равны по численности, выборка репрезентативна для всех кандидатов. Это
сверка «дешёвый судья против дорогого»: 8B-модель за один forward-проход против модели, которая рассуждает
перед ответом. Сильная модель тоже не эталон, поэтому измеряется согласованность, а не точность. Тот же
скрипт строит страницу для ручной разметки, если появится разметчик-человек. `report.py` считает ρ Спирмена,
AUC судьи на задачах «хороший / остальные» и «плохой / остальные» и главное для отбора — долю плохих
рецептов среди отобранных и среди отброшенных, всё с бутстрэп-интервалами.

| Показатель | Значение [95% ДИ] |
|---|---|
| ρ Спирмена, судья и DeepSeek | 0.41 [0.24; 0.55] |
| AUC: хорошие (≥ 4 по DeepSeek) против остальных | 0.69 [0.59; 0.78] |
| AUC: плохие (≤ 2 по DeepSeek) против остальных | 0.75 [0.57; 0.90] |
| Доля плохих (≤ 2): отобранные / отброшенные | 4% [0; 10] / 13% [5; 21] |
| Доля хороших (≥ 4): отобранные / отброшенные | 72% [59; 84] / 50% [38; 62] |

Ранжирует судья неточно, но для отбора важнее, чтобы в обучение не попадали плохие рецепты, и здесь
направление правильное. На 120 рецептах интервалы широкие. Следующий шаг — человеческая разметка 30–50
рецептов, в первую очередь тех, где судья и DeepSeek расходятся сильнее всего.

![Судья против DeepSeek](eval/figures/judge_validation.png)

Запросы в обучении трёх типов: по названию (50%), по продуктам (30%, 2–4 нетривиальных продукта из
рецепта), по категории или поводу (20%). Loss считается только на ответе.

## Модели и обучение

- **LoRA** r=16, α=32 на все линейные слои внимания и MLP, fp16 (на V100 нет bf16), SDPA-внимание,
  gradient checkpointing, effective batch 16, lr 1e-4 cosine, 2 эпохи, `max_seq_len` 1536. В конце
  загружается лучший чекпоинт по `eval_loss`. Обе модели учатся одинаково на одних и тех же данных.
- **Формат чата YandexGPT нестандартный**: ` Пользователь: … Ассистент:[SEP]`, system-роли нет, переводы
  строк кодируются токеном `[NL]`. Класс `recipe_llm/chat.py` строит промпт штатным шаблоном модели, а ответ
  кодирует отдельно с EOS. Один и тот же код используется в обучении, судье, оценке и демо, поэтому форматы
  не расходятся. Если у шаблона нет system-роли, инструкция переносится в реплику пользователя.

![Кривые обучения](eval/figures/training.png)

Eval loss выходит на плато примерно к 125-му шагу из 1214: у YandexGPT 1.865 → 1.149 за первые 125 шагов
и лишь до 1.128 за оставшиеся 1100 (у Qwen 1.322 → 1.001 → 0.936). Почти всё полезное модель выучивает за
первые 10% первой эпохи, и это согласуется с выводом 3: она перенимает формат, а не знания. Одной эпохи
было бы достаточно.

## RAG

- **Индекс** (`scripts/build_rag_index.py`): все рецепты povarenok.ru, прошедшие те же правила, без
  отсечения по популярности, с дедупом. Эмбеддинги `intfloat/multilingual-e5-large` по названию,
  ингредиентам и началу шагов. Поиск — точный косинусный по всей матрице на GPU (при таком объёме FAISS
  не нужен) с небольшим бонусом за популярность.
- **Промпт** (`recipe_llm/rag.py`): 3 найденных рецепта и инструкция «используй как опору, исправь ошибки,
  не копируй; если не подходят — опирайся на свои знания».
- **Отдельная метрика поиска**: есть ли у первого найденного рецепта ключевые ингредиенты блюда или
  продукты из запроса (`retrieval_quality` в `eval/RESULTS.md`). Так ошибки поиска отделяются от ошибок
  генерации.

## Оценка

Фиксированный набор `eval/prompts.jsonl` из 200 запросов: 75 классических блюд с регулярками ключевых
ингредиентов (от борща до хумуса и тирамису), 70 наборов продуктов и 55 категорий и поводов. Декодирование
жадное, одинаковое для всех систем.

| Метрика | Что проверяет |
|---|---|
| Ключевые ингредиенты | для классики: в борще есть свёкла и капуста, в сырниках творог |
| Продукты из запроса | «у меня есть X, Y» — X и Y действительно использованы |
| Ингредиенты в шагах | всё из списка ингредиентов используется в приготовлении |
| Количества | у ингредиентов указаны количества |
| «Болтовня» | «очень вкусно!», «приятного аппетита», «всем советую», истории «у меня была…» |
| Обрывы | ответ упёрся в лимит токенов |
| Структура / фирменный формат | есть ≥2 ингредиента и ≥2 шага / ответ в целевом markdown-формате |

**Статистика** (`scripts/report.py`). Для каждой метрики считается 95% перцентильный бутстрэп по запросам
(B = 10 000). Эффекты считаются парным бутстрэпом: ресэмплируются id запросов, и на каждом ресэмпле
берётся разница средних двух систем. Так межзапросная дисперсия уходит, и интервалы получаются намного
уже, чем при сравнении двух независимых ДИ. Поправки на множественные сравнения нет, поэтому отметки
значимости — ориентир для внимания, а не подтверждающий тест.

**SBS** (`scripts/make_sbs.py`) — автономная HTML-страница для слепого сравнения. Ответы двух систем
показываются в случайном порядке, разметка клавишами 1/2/3, на выходе JSON. `report.py` считает по нему
win rate с бутстрэп-интервалом. Автометрики эвристические и кулинарную бессмыслицу ловят не полностью:
например, «сырники» дообученного Qwen без муки, запечённые в формочках, проходят все проверки.

## Как это мерить онлайн

Живых пользователей у пет-проекта нет, поэтому онлайн-эксперимента нет. Если бы генератор встраивался в
кулинарный сервис, A/B-тест выглядел бы так:

- **Единица рандомизации — пользователь**, а не запрос: стабильный хеш от id. Иначе один человек видит
  обе версии, и эффекты смешиваются.
- **Целевая метрика** — доля пользователей, сохранивших рецепт, добавивших продукты в список покупок
  или открывших пошаговый режим. Сам факт генерации не показатель: модель, которая чаще ошибается,
  вызывает больше перегенераций.
- **Барьерные метрики**: доля дизлайков и перегенераций, жалобы, p95 задержки, стоимость запроса.
- **Статистика**: метрики-отношения на пользователя считаются дельта-методом или бутстрэпом по
  пользователям. Дисперсию снижает CUPED с активностью до эксперимента.
- **Размер выборки**: при базовой доле 30% и минимальном детектируемом эффекте +1 п.п. (α = 0.05,
  мощность 80%) нужно n ≈ 2·(1.96 + 0.84)²·0.3·0.7 / 0.01² ≈ 33 тыс. пользователей на группу.
- **Длительность — не меньше двух недель** с разбивкой эффекта по дням: так видно, затухает ли эффект новизны.
- **Связь с офлайном**: перед раскаткой проверить, что офлайн-победитель (SBS, автометрики) выигрывает
  и онлайн. Если нет — офлайн-метрики меряют не то. Лайки и дизлайки из продукта — готовая разметка
  для следующей калибровки судьи.

## Демо

```bash
python app.py --adapter outputs/yandexgpt5-recipes/final_adapter --rag data/rag_index --share
```

В Gradio-приложении есть режимы «Блюдо», «Из продуктов», «Категория» и свободный запрос, стриминг ответа,
переключатель RAG со списком найденных рецептов и сравнение с базовой моделью в один клик. Для сравнения
LoRA отключается на лету, поэтому вторая копия весов в памяти не нужна. В CLI те же возможности:
`python infer.py --adapter … --rag data/rag_index --prompt "Борщ"`.

## Как воспроизвести (Slurm, V100 32GB, все задачи на 1 GPU)

```bash
# 0. окружение и загрузки (логин-нода с интернетом)
conda create -n llm python=3.11 -y && conda activate llm
pip install torch==2.14.1 --index-url https://download.pytorch.org/whl/cu126   # последняя сборка с sm_70
pip install -r requirements.txt
python scripts/prefetch.py --models yandex/YandexGPT-5-Lite-8B-instruct Qwen/Qwen2.5-7B-Instruct \
                           --encoders intfloat/multilingual-e5-large

# 1. данные -> судья (4 шарда) -> обучение обеих моделей -> оценка 4 систем
bash slurm/run_all.sh
# 2. RAG-индекс -> оценка 4 систем с RAG
bash slurm/run_rag.sh
# 3. (пере)оценка всех 8 систем на текущем наборе запросов; готовые ответы переиспользуются (--resume)
bash slurm/run_eval.sh
# 4. проверка судьи: выборка 120 рецептов -> eval/judge_labeling.html; разметка (человек или сильная модель)
#    -> eval/judge_labels.json с полем "annotator"
python scripts/make_judge_labeling.py
# 5. отчёт: таблицы с ДИ, парные эффекты, проверка судьи, графики -> eval/REPORT.md, eval/figures/
python scripts/report.py
# опционально: слепое сравнение (60 случайных запросов), затем снова report.py
python scripts/make_sbs.py yandex-base yandex-ft
```

Скрипты `run_*.sh` только ставят задачи в очередь `sbatch` с зависимостями `afterok`; вычисления идут
в задачах. Без Slurm те же скрипты запускаются напрямую (`python train.py --config …`). MLflow хранит всё
в `mlflow.db`, интерфейс: `bash scripts/mlflow_ui.sh`.

Тесты на CPU без загрузок: крошечные модели с форматами Qwen и YandexGPT прогоняют весь пайплайн —
данные, судью, обучение, оценку, RAG, отчёт, CLI и демо (`bash tests/pipeline_test.sh`, `bash tests/smoke_test.sh`).

## Ограничения

- Судья — та же YandexGPT, что дообучается, поэтому отбор может смещаться к её вкусам. Человеческой разметки
  нет: судья сверен с более сильной LLM, которая тоже не эталон и может разделять систематические ошибки
  LLM-оценщиков.
- Автометрики проверяют форму и наличие ингредиентов по основам слов, а не кулинарную корректность.
- Интервалы учитывают разброс по запросам, но не по сидам обучения: каждая модель обучена один раз.
  Одна генерация на запрос, жадное декодирование; разброс при сэмплировании не оценивался.
- Данные — пользовательские рецепты, у `dim/povarenok` лицензия не указана.
